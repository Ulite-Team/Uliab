## Candidate phases — surfaced during real-project (NoteScribe) build planning, 2026-08-21
Not yet scoped into numbered phases, not started, not prioritized against items 1–2 above.
Recorded here so they aren't lost before the NoteScribe trial build surfaces them again the hard way.
Grouped by how soon a real Compose Android app build would actually hit them:

**Would block a first real build immediately:**
- Compose compiler plugin invocation — `ulite/android`/`ulite/jvm` currently drive plain `kotlinc`; any `@Composable` source needs the Compose compiler plugin artifact + flags wired into that `kotlinc` invocation, or every real UI module fails at first compile.
- Product flavors / build-variant matrix (`buildTypes` × `productFlavors` dimensions, per-variant source-set layering, down-module variant propagation) — ARCHITECTURE.md §5.2 describes this; only a single build-type flow (signing/packaging) is implemented so far, no flavor dimension handling.
- Rust/JNI native module support (relevant to NoteScribe specifically: a Rust/JNI backend module) — cross-compiling a Rust crate per Android ABI and packaging the resulting `.so` files into `jniLibs/<abi>/` inside the APK/AAR. Needs NDK toolchain discovery (same shape as the existing Android SDK discovery, §3.2) plus a `cargo`/NDK-`clang` entry in `AllowlistedTool`.

**Would surface within the first few real builds:**
- BuildConfig generation (`buildConfigField`-style codegen) — common for per-variant API keys/base URLs; a separate codegen step from the variant matrix above.
- Dependency excludes + BOM/`dependencyManagement` support in the Maven resolver — BOM support is implemented; dependency excludes not yet supported.
- JDK auto-discovery — Android SDK discovery exists (§3.2); nothing analogous locates a JDK yet, so `javac`/`kotlinc` invocation implicitly relies on `PATH`.
- Local/composite builds across separate repos — different from the same-repo `project(":module")` refs done in Phase 10: sharing code between Amr's separate real projects (NoteScribe, Apex, Ulite SaaS) needs building against a sibling repo's local (unpublished) output.

**Would matter before a public/CI-driven release, not before:**
- R8/minification (and the crash-symbolication follow-on: preserving/consuming `mapping.txt`) — signing (Phase 11) assumes an unminified APK.
- AAB (Android App Bundle) packaging — Play Store publishing needs `.aab`, not the raw `.apk` the packaging slice produces today.
- Dependency lockfile — the resolver re-resolves dynamically each run; without a lockfile, a build today can resolve a different transitive version than the same build next month.
- Watch mode (rebuild on file change) and `adb install`/run-on-device integration — day-to-day dev-loop ergonomics, not build correctness.
- Explicit offline/CI-verification mode — `file://`/local-path Maven repos already make offline resolution possible (Phase 7c), but there's no explicit flag/check that asserts a build ran with zero network access, which a CI pipeline would want to enforce rather than merely allow.

**Not a gap — already covered by existing capability, worth remembering when testing NoteScribe:**
- Reading a git commit hash and detecting whether the build is running in GitHub Actions CI need no new phase — both are readable today via the existing `env()` builtin (Phase 4) against whatever variables the CI environment sets (e.g. `GITHUB_SHA`, `GITHUB_ACTIONS`), exactly like the `signing {}` env-conditional example from GRAMMAR.md's worked examples.
